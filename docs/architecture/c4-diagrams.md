# Auto-Flashcards — C4 Архитектура

## 1. Context (Система и внешний мир)

![System Context](/docs/architecture/img/context.png)

**Главный актор:** Студент (пользователь).  
**Внешние системы:**

- **LLM-провайдер** — генерация карточек (Q/A) и извлечение ключевых понятий.
- **OCR/NLP сервис** — извлечение текста из PDF/изображений.
- **Auth/IdP** (опционально) — аутентификация и управление сессиями.
- **Файловое хранилище** — загрузка исходных материалов (PDF/текст).

**Потоки взаимодействия (высокоуровнево):**

1. Студент → Auto-Flashcards: загрузка материала / работа с колодами / SRS / статистика / профиль.
2. Auto-Flashcards → LLM/OCR: фоновые запросы для генерации/извлечения.
3. Auto-Flashcards → Хранилище: сохранение исходных файлов и результатов.

## 2. Container (Основные компоненты системы)

![Container Diagram](/docs/architecture/img/container.png)

**Frontend (Next.js/React)**

- UI для UC-1..UC-5: импорт, предпросмотр, редактор карточек, SRS-сессия, статистика, профиль.
- Состояния: загрузка/ошибка/успех, уведомления, подтверждения.

**API Backend (FastAPI)**

- REST/OpenAPI-контракты.
- Реализация логики UC-1..UC-5.
- Вызовы LLM/OCR через **LLM Gateway**.
- Планировщик/очередь для фоновых задач (импорт/генерация, OCR).

**LLM Gateway (Сервис-обёртка)**

- Единая точка интеграции с LLM-провайдерами.
- Троттлинг, ретраи, логирование стоимости, анонимизация данных.

**OCR Service (адаптер/интеграция)**

- Извлечение текста из PDF/изображений.
- Валидация и нормализация текста.

**DB (PostgreSQL)**

- Users, Decks, Cards, Reviews(SRS), Stats, LLM/OCR Jobs.
- Индексы по deckId, nextReviewAt, агрегаты для статистики.

**Object Storage (например, S3-совместимое)**

- Исходные материалы (PDF/текст) и промежуточные артефакты.

**Monitoring/Tracing**

- Метрики latency/ошибок/стоимости LLM, трассировка запросов, дашборды.

## 3. Связь UC ↔ Контейнеры ↔ Эндпоинты (обзор)

- **UC-1 Создание колоды:**  
  Frontend → API: `POST /decks` (+ загрузка `fileRef|rawText`),  
  API → LLM/OCR (через Gateway/адаптер),  
  API → DB: создание Deck + Cards,  
  Frontend → API: `GET /decks/{id}/cards` (предпросмотр/редактура).
- **UC-2 Редактирование:**  
  Frontend → API: `PATCH /cards/{id}`, `POST /cards/merge`,  
  API → DB: изменение/слияние, разрешение конфликтов версий.
- **UC-3 SRS-сессия:**  
  Frontend → API: `POST /srs/session/start`, `POST /srs/grade`,  
  API → DB: выбор карточек «к сроку», пересчёт интервалов.
- **UC-4 Статистика:**  
  Frontend → API: `GET /stats?range=...&deck=...`,  
  API → DB: агрегаты/кэш, выдача рекомендаций.
- **UC-5 Профиль:**  
  Frontend → API: `GET/PUT /profile`,  
  API → DB: валидация и сохранение настроек.

## 4. Нефункциональные аспекты на уровне контейнеров

- **Производительность:** P95 ≤ 800 мс для интерактивных экранов; фоновые операции — в очередях.
- **Надёжность:** ретраи/таймауты для LLM/OCR, автосохранение прогресса SRS.
- **Безопасность/приватность:** TLS, минимизация передаваемых данных LLM, контроль доступа к Decks/Cards.
- **Наблюдаемость:** логирование бизнес-событий, трассировка вызовов LLM, дашборды.
- **Стоимость:** лимиты на частоту LLM, учёт затрат по пользователям/колодам.

## 5. Решения и альтернативы (ADR кратко)

- Язык/фреймворк API: FastAPI (альтернатива: Node/Express/Nest) — выбран за скорость прототипирования и типизацию.
- БД: PostgreSQL (альтернатива: MongoDB) — из-за отношений Decks↔Cards, агрегатов и транзакций.
- LLM-провайдер: провайдер X (резерв: провайдер Y) — через абстракцию Gateway для взаимозаменяемости.
- Очереди: Celery/RQ/Sidekiq-аналог — отделение долгих задач импорта/генерации.
- Мониторинг: Prometheus+Grafana и трассировка LLM (например, Langfuse).
