Auto-Flashcards — Определения DoR/DoD и KPI

1. Definition of Ready (DoR)

История считается готовой к разработке, если выполнены все пункты:

Связь с UC: История привязана к конкретному Use Case (UC-1…UC-5) и содержит проверяемые критерии приёмки (AC).

Дизайн/UX: Есть wireframes/flows для экранов (если применимо) и тексты UX-сообщений (ошибки/пустые состояния).

Контракты: Подготовлен черновик OpenAPI (эндпоинты, схемы запрос/ответ), понятны коды ошибок.

Данные: Определены входные данные/валидации и тестовые примеры (happy path + 2–3 edge cases).

NFR-цели: Зафиксированы целевые значения: P95 latency, надёжность (автосохранение/ретраи), наблюдаемость (метрики/логи/трейсы), лимиты стоимости LLM.

Зависимости/риски: Отмечены внешние зависимости (LLM/OCR/Auth/Storage), риски и стратегия смягчения (retry/timeout/limit).

Оценка/приоритет: Оценён объём (story points/timebox), приоритет согласован с roadmap.

2. Definition of Done (DoD)

История/функция считается выполненной, если:

AC выполнены (по UC):

UC-1 (Создание колоды): импорт укладывается в целевое время (≤ 60s для типового файла), ≥ 30 заготовленных карточек для ~20 страниц, дружелюбные сообщения при ошибках формата/размера/языка, предпросмотр/сохранение работают.

UC-2 (Редактирование): правки вопрос/ответ/сложность сохраняются без потери данных; объединение дублей; обработка конфликтов версий (выбор/merge); валидации и подсказки при пустых полях.

UC-3 (SRS-сессия): корректный выбор карточек «к сроку»; пересчёт интервалов по оценке (again/hard/good/easy); прогресс не теряется при обрыве; итоговая сводка сессии.

UC-4 (Статистика): корректные агрегаты; фильтры и периоды (day/week/month) без заметных задержек; понятное «Недостаточно данных».

UC-5 (Профиль): валидации полей (имя/язык/тема/уровень), сохранение без ошибок; подтверждения перед сбросом прогресса.

NFR достигнуты:

Производительность: P95 latency для интерактивных экранов ≤ 800 мс; тяжёлые операции — во фоновых задачах.

Надёжность: автосохранение прогресса SRS; ретраи/таймауты для LLM/OCR; идемпотентность критичных операций.

Наблюдаемость: метрики latency/error/cost LLM; технические/бизнес-логи; трассировка ключевых вызовов (LLM/OCR).

Безопасность/приватность: TLS; минимизация/анонимизация отправляемых данных; контроль доступа к Decks/Cards.

Стоимость: rate limiting/батчинг запросов к LLM; базовый учёт затрат на пользователя/колоду.

Качество:

Unit/интеграционные тесты пройдены (включая негативные сценарии); ручной прогон happy-path.

Код отлинтен/отформатирован; покрытие тестами на уровне, согласованном с командой.

Документация:

OpenAPI актуален; добавлены примеры запрос/ответ; описаны коды ошибок.

Обновлены пользовательские тексты ошибок/пустых состояний.

CI/CD: пайплайн зелёный; сборка dev-окружения (docker-compose.dev) без ошибок.

Ревью: выполнено peer review, замечания устранены; SA/PO подтвердил соответствие AC/NFR.

3. KPI и целевые значения

Продуктовые и технические показатели:

UC-1 — Импорт/генерация:

Успешные импорты (без ошибок), % ≥ 95%.

Среднее/Р95 время обработки ≤ 60s для типового файла.

UC-3 — SRS:

% завершённых сессий без потери прогресса ≥ 99%.

Корректность пересчёта интервалов (выборочная проверка) ≥ 98%.

UC-4 — Статистика:

P95 ответа панели ≤ 800 мс; корректность агрегатов (выборочные сверки) ≥ 99%.

Качество LLM:

Доля карточек, принятых пользователем без правок (после предпросмотра) ≥ 70% на базовом датасете.

Надёжность/стоимость:

Error rate (5xx) < 1%; соблюдение лимитов LLM; отчёт по стоимости раз в спринт.

4. Матрица приёмки (сводная по UC)

| UC   | Ключевые AC (сжатая формулировка)                                        | Проверка                                      |
| ---- | ------------------------------------------------------------------------ | --------------------------------------------- |
| UC-1 | Импорт ≤ 60s; ≥ 30 карт/20 стр.; ошибки понятны; предпросмотр/сохранение | Тесты импорта + ручная проверка предпросмотра |
| UC-2 | Правки/merge без потерь; конфликт версий обработан; валидные ошибки      | Unit на валидации + интегр. тесты правок      |
| UC-3 | Выбор «к сроку»; корректный пересчёт; прогресс сохранён                  | Интегр. сценарий с разрывом соединения        |
| UC-4 | Корректные агрегаты; быстрые фильтры/периоды; пустые состояния           | Нагрузочные/выборочные сверки                 |
| UC-5 | Валидации профиля; сохранение; подтверждение сброса                      | Тесты валидации + ручная проверка             |

## 5. Гейт NFR (выпуск допускается, если все пункты «да»)

- [ ] P95 интерактивных эндпоинтов ≤ **800 мс** на стенде dev.
- [ ] UC-1 выполняется в пределах целевого времени на типовых файлах.
- [ ] Автосохранение прогресса SRS подтверждено тестом «обрыв соединения».
- [ ] Метрики/логи/трейсы доступны в мониторинге; ошибки LLM/OCR наблюдаемы.
- [ ] Rate limiting/ретраи активны; нет перерасхода лимитов LLM.
- [ ] Безопасность: TLS, валидации входных полей, доступ к данным по ролям/владению.

## 6. Стратегия тестирования (кратко)

- **Unit:** валидации, парсинг/схемы, расчёт SRS-интервалов.
- **Интеграционные:** импорт (моки OCR/LLM), редактирование/merge, SRS-сессия, статистика.
- **Нагрузочные:** `/stats`, списки карт/колод; оценка индексов и кэшей.
- **UX/ручные:** тексты ошибок, «нет данных», конфликт версий, happy-path по всем UC.

## 7. Release Readiness (Go/No-Go чек-лист)

- [ ] Все AC по UC-1..UC-5 закрыты.
- [ ] NFR-гейт пройден.
- [ ] CI зелёный; `docker-compose.dev` стартует без ошибок.
- [ ] OpenAPI актуален; примеры запрос/ответ проверены.
- [ ] Документация пользователя и операционная памятка обновлены.
- [ ] Риски и митигации отражены в roadmap/ADR.

8. ADR и трассировка решений

Основные архитектурные решения (API-фреймворк, БД, LLM-провайдер, стратегия очередей, мониторинг) оформлены в ADR (шаблон: проблема → альтернативы → решение → рационал → влияние/риски).

Каждое требование из requirements связано с UC и эндпоинтами OpenAPI (traceability).

9. Примечания по соблюдению приватности и стоимости

Минимизировать и анонимизировать данные, отправляемые в LLM/OCR; не пересылать лишний контент.

Логировать «стоимость» вызовов LLM на уровне пользователя/колоды; отчёт в конце спринта; верхние лимиты зафиксированы.

Ответственные за приёмку:
SA/PO (соответствие AC/NFR), Tech Leads (качество/надёжность), QA (тесты), MLOps (наблюдаемость/пайплайн), Fullstack (UI/UX/контракты), AI Engineer (качество LLM).
