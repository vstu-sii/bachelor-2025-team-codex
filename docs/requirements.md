Auto-Flashcards — Требования (requirements.md)

1. Область и цели

Система: Auto-Flashcards
Цель продукта: Превращать учебные материалы (PDF/текст/видео) в набор карточек «вопрос-ответ», обеспечивать ежедневные сессии интервального повторения (SRS), отслеживать прогресс и предоставлять понятные отчёты.
Границы системы: Ввод материалов → извлечение текста (OCR/NLP) → генерация карточек (LLM) → редактирование → повторение (SRS) → статистика → профиль/настройки.

2. Роли и термины

Студент (Пользователь): создаёт и изучает карточки.

Внешние AI-сервисы: LLM для генерации карточек; OCR/NLP для извлечения текста.

SRS: интервальное повторение (алгоритм на основе SM-2/аналог).

3. Объём MVP (высокоуровнево)

Импорт учебного материала и создание колоды (UC-1).

Базовое редактирование карточек (UC-2).

Ежедневная SRS-сессия с оценкой запоминания (UC-3).

Базовая панель прогресса (UC-4).

Профиль/настройки (язык/тема/уровень) (UC-5).

4. Функциональные требования (FR) по Use Case
   4.1 UC-1 — Создание набора карточек

FR-1.1 Пользователь может загрузить файл (PDF/текст) размером ≤ 25 MB.
FR-1.2 Система извлекает текст (OCR/NLP при необходимости).
FR-1.3 Система генерирует первичный набор карточек «вопрос-ответ».
FR-1.4 Предпросмотр набора с возможностью удалить/отредактировать карточки до сохранения.
FR-1.5 Сохранение набора в профиле пользователя.

Критерии приёмки (AC):

AC-1: Время обработки файла ≤ 60 сек для стандартной лекции.

AC-2: Для лекции ~20 страниц система генерирует ≥ 30 карточек (до редактирования).

AC-3: Понятные сообщения об ошибках при: превышении размера, неподдерживаемом формате, нераспознанном тексте/языке.

AC-4: Успешно сохранённый набор виден в списке наборов.

4.2 UC-2 — Редактирование и улучшение набора

FR-2.1 Открытие существующего набора и списка карточек.
FR-2.2 Редактирование вопроса/ответа/сложности карточки.
FR-2.3 Объединение дубликатов карточек.
FR-2.4 Отмена изменений (undo) до сохранения.
FR-2.5 Разрешение конфликтов версий при одновременном редактировании с разных устройств.

Критерии приёмки (AC):

AC-1: Сохранение не приводит к потере данных.

AC-2: При пустых/некорректных полях — понятная ошибка с подсветкой.

AC-3: При конфликте версий предлагается объединение/выбор актуальной версии.

4.3 UC-3 — Ежедневная SRS-сессия

FR-3.1 Выбор карточек, срок повторения которых наступил.
FR-3.2 Отображение вопроса → раскрытие ответа.
FR-3.3 Оценка запоминания: Плохо / Трудно / Хорошо / Легко.
FR-3.4 Пересчёт интервала следующего повторения по алгоритму SRS (основан на SM-2/эквивалент).
FR-3.5 Статистика по завершении сессии (количество, % правильных).

Критерии приёмки (AC):

AC-1: Прогресс не теряется при разрыве соединения/закрытии сессии.

AC-2: Интервалы повторов обновляются корректно согласно оценке.

AC-3: При отсутствии карточек на сегодня показывается понятное сообщение.

4.4 UC-4 — Просмотр статистики и прогресса

FR-4.1 Панель статистики: количество карточек, % правильных ответов, активность.
FR-4.2 Выбор периода: день / неделя / месяц.
FR-4.3 Фильтры по темам/наборам.
FR-4.4 Рекомендации по слабым темам.

Критерии приёмки (AC):

AC-1: Корректность данных и агрегатов.

AC-2: Фильтры и переключение периодов работают без заметных задержек.

AC-3: При отсутствии данных — информативное сообщение «Недостаточно данных».

4.5 UC-5 — Управление профилем

FR-5.1 Просмотр и изменение настроек профиля: имя, язык интерфейса, тема, уровень сложности.
FR-5.2 Валидация полей, сохранение изменений, подтверждения перед сбросом прогресса.
FR-5.3 Сообщения об ошибках при некорректных данных.

Критерии приёмки (AC):

AC-1: Корректный ввод сохраняется без ошибок.

AC-2: Неверный ввод подсвечивается и сопровождается подсказкой.

AC-3: Сброс прогресса требует явного подтверждения.

5. Нефункциональные требования (NFR)
   5.1 Производительность

Latency (P95) для интерактивных операций (редактирование, навигация, статистика): ≤ 800 мс.

Импорт/генерация (UC-1): укладываться в AC-порог (обычно ≤ 60 сек).

Эффективные индексы/кеширование для экранов статистики и списков.

5.2 Надёжность и отказоустойчивость

Прогресс SRS не теряется при обрыве (автосохранение чекпоинтов).

Повтор запросов к внешним сервисам (LLM/OCR) с экспоненциальной паузой.

Чёткая деградация при недоступности внешних сервисов (сообщение пользователю, сохранение черновика).

5.3 Безопасность и приватность

Защита персональных данных, шифрование в движении (TLS).

Минимизация отправки чувствительной информации во внешние сервисы (LLM/OCR); анонимизация по возможности.

Контроль доступа к наборам/карточкам только владельцу.

5.4 Наблюдаемость (Observability)

Логи событий (импорт, генерация, ошибки), трассировка LLM-запросов.

Метрики по latency/ошибкам/стоимости вызовов LLM.

Дашборды мониторинга (ошибки, пропускная способность, успешность сессий SRS).

5.5 Масштабируемость

Горизонтальное масштабирование API и очередей задач генерации/ОCR.

Отделение долгих задач (OCR/LLM) в фоновые джобы.

5.6 Стоимость

Лимиты на частоту обращений к LLM/OCR; троттлинг и группировка запросов.

Учёт стоимости на пользователя/набор/спринт; еженедельные отчёты.

6. Интерфейсы (черновой контракт API)

Окончательная спецификация — в OpenAPI, здесь зафиксирован обязательный минимум.

UC-1:

POST /decks — создать набор (поля: title, fileRef|rawText). Ответ: 201 { deckId }.

GET /decks/{id}/cards — предпросмотр/получение сгенерированных карточек.

UC-2:

PATCH /cards/{id} — изменить вопрос/ответ/сложность.

POST /cards/merge — объединить дубликаты (по cardIds/правилам).

UC-3:

POST /srs/session/start — выдать карточки к повторению на сегодня.

POST /srs/grade — принять оценку и пересчитать интервал.

UC-4:

GET /stats?range=day|week|month&deckId=... — агрегаты/метрики/рекомендации.

UC-5:

GET /profile, PUT /profile — получить/обновить настройки пользователя.

7. Модель данных (высокоуровнево)

Users(id, email, displayName, createdAt)

Decks(id, userId, title, createdAt)

Cards(id, deckId, question, answer, difficulty, createdAt)

SRS_Sessions / Reviews(id, userId, deckId, cardId, grade, nextReviewAt, updatedAt)

Stats(userId, date, counts…) — агрегированные метрики/кэши

LLM/OCR_Jobs(id, deckId, status, cost, error, createdAt)

Индексы: cards(deckId), reviews(cardId,nextReviewAt), агрегаты по userId/date.

8. Бизнес-правила и алгоритмы

Алгоритм SRS: основан на SM-2 (или эквивалент) с параметризацией под 4 оценки (Плохо/Трудно/Хорошо/Легко).

При «Плохо» интервал сокращается/сбрасывается; при «Легко» — растёт быстрее.

Пропуск карточки возможен — карточка уходит в конец очереди текущей сессии.

9. Обработка ошибок (сводка)

Импорт/генерация: нет сети / таймаут LLM / превышение размера → понятные сообщения, повтор/очередь, сохранение черновика.

Редактирование: конфликт версий → выбор стратегии (объединить/переписать); пустые поля → подсветка и подсказки.

SRS: сбой расчёта интервала → дефолтное значение, логирование.

Статистика: нет данных → дружелюбное уведомление, подсказка выполнить хотя бы одну сессию.

10. Метрики и KPI

Создание колоды (UC-1): % успешных импортов без ошибок; среднее и P95 время обработки.

SRS (UC-3): % завершённых сессий без потери прогресса; точность пересчёта интервалов.

Статистика (UC-4): P95 времени ответа панели (в пределах цели), корректность агрегатов.

Качество LLM: доля карточек, оставшихся после пользовательской ревизии (валидность/полезность).

Ошибки/UX: снижение жалоб на непонятные сообщения об ошибках к ~0.

11. Риски, допущения, зависимости

Зависимость от LLM/OCR: недоступность/таймауты/стоимость → очереди/ретраи, лимиты, резервный провайдер, анонимизация данных.

Нагрузка на статистику: тяжёлые фильтры → индексы, агрегации, кэш.

Конкурентное редактирование: конфликты версий → механика merge/lock, ясные подсказки в UI.

Приватность: хранить только необходимые данные, полиси по удалению и экспорту.

12. Критерии приёмки релиза (Product DoD)

Реализованы FR для UC-1…UC-5 по AC.

Выполнены NFR: Latency P95 ≤ 800 мс (интерактив), устойчивость к разрывам, логирование и метрики.

Docker-окружение собирается и запускается без ошибок; API покрыт базовыми тестами.

OpenAPI соответствует фактическим контрактам; примеры запрос/ответ актуальны.

Демонстрационный сценарий (happy-path): импорт → предпросмотр → редактирование → SRS → статистика — проходит без сбоев.

Документация пользователя и операционная памятка (ошибки/ограничения) обновлены.

Примечания:

Все сообщения ошибок должны быть понятными и дружественными.

Для каждой истории — ясные AC, проверяемые вручную и автотестами.

ADR фиксирует ключевые архитектурные решения (выбор технологий, провайдер LLM и т. п.).
